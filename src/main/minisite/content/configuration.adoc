== HTTP redirects

Redirects are handled differently depending on the destination:

* *Scraped endpoints* follow redirects by default.
It can be disabled per scraper with `followRedirects=false`, the `3xx` response is then compared to `expectedResponseCode`.
When a redirect leads to another host, `Authorization` is not sent to it but the other `headers` are, so a warning is logged:
prefer the final URL or disable `followRedirects` if the redirect is not expected.
* *Elasticsearch* calls never follow redirects since Elasticsearch does not redirect by itself: a `3xx` comes from a proxy or a wrong `elasticsearch.base`.
Following it would replay a `_bulk` `POST` as a `GET` without payload, so it fails with an explicit error and `elasticsearch.base` must be set to the final URL.

[source,bash]
----
# keep the 3xx of this scraper instead of following it
METRICS_SCRAPER_SCRAPERS_0_FOLLOWREDIRECTS="false"
----

== HTTP client

The HTTP client uses non-blocking I/O (`java.net.http`), so a few threads (`threading.core`, `4` by default) are enough to complete many concurrent requests, `threading.max` is ignored.

* `http.connectTimeout` bounds the connection establishment (`30s` by default).
* `http.defaultTimeout` is the request timeout used when a scraper or Elasticsearch sets `timeout=0` (`60s` by default), set it to `0` to really have no timeout.
* `http.logExchanges` (enabled by default) logs each HTTP request as a replayable `curl` command, using the `io.yupiik.metrics.scraper.http.exchanges` logger.
Sensitive headers (`Authorization`, cookies, API keys and every configured `headers` of Elasticsearch and the scrapers) are masked and payloads are not logged.

[source,bash]
----
# silence the exchange logs
METRICS_SCRAPER_HTTP_LOGEXCHANGES="false"
----

== Stop

The Docker image sets `-Dfusion.launcher.useHook=true` so a `SIGTERM` stops the application properly,
set it too when launching `io.yupiik.fusion.framework.api.main.Launcher` yourself.

The stop is graceful, in this order:

. no new scraping is started and the in-flight ones can finish during `stopGracePeriod` (`5s` by default, so it fits the `10s` of `docker stop`), then they are cancelled,
. the collectors flush their pending Elasticsearch bulks (up to one minute),
. the HTTP client is closed.

Keep the orchestrator grace period (`docker stop -t`, Kubernetes `terminationGracePeriodSeconds`) above it, the process is killed otherwise.
